# 缺陷子图标签 → 原图总库 映射工具

把人工在**缺陷子图**上清洗过的标注（增、删、改类别、调框），安全地回写到**原图总库**的缺陷 XML 里。

---

## 一、一分钟看懂

### 问题是什么

两阶段算法的流程是：先在原图上检测部件 → 按部件框裁出子图 → 在子图上识别缺陷。
所以我们有两套标注：

```
原图总库 Annotations/          子图数据集 gd_data/Annotations/
  某张原图.xml         ──裁切──▶  某张原图_gd_0.xml
  (缺陷坐标是原图坐标)             (缺陷坐标是子图坐标)
                                  某张原图_gd_1.xml
                                  ...
```

人工只在**子图**上做清洗。清洗成果保存在子图 XML 里，**原图总库还是旧标签**。
一旦重新裁切，所有清洗成果全部作废。这个工具就是把子图的改动"翻译"回原图。

### 为什么不能直接坐标平移

裁切不是简单的复制，中间做了 5 件会丢信息的事：


| 裁切时做的事                                                   | 带来的麻烦                               |
| -------------------------------------------------------- | ----------------------------------- |
| 部件框被**扩充**（jyz 长边 +35%/短边 +45%，gd +20%/+20%）             | 子图范围 ≠ 部件框，偏移量必须从 `crop_mapping` 里读 |
| 缺陷要过**面积阈值**才被裁进子图                                       | 原图里有、子图里没有的缺陷，人工看不到                 |
| 跨出部件框的缺陷被**截断**（`was_clipped=true`）                      | 子图里只有半截框，人工是对着半截框作业的                |
| gd 有**不可逆类别映射**（`lmsd`/`xjjsd`/`gt_bmqk` → 都变成 `lslmqk`） | 从子图反查不出原图的细分类名                      |
| 部件框互相重叠，**一个缺陷会被多个子图裁到**                                 | 各子图的清洗结果可能互相矛盾                      |




### 工具怎么解决

核心思路：**能百分百确定的自动写，有一点点拿不准的全部拦下来交人工看图确认。**

```
                          ┌──────────────┐
   子图 XML（清洗后）  ──▶ │              │──▶ changeset.json ──▶ 自动写入原图
   crop_mapping.json  ──▶ │  1_生成变更集 │
   原图 XML（当前）    ──▶ │   （只读）    │──▶ review_queue.json ──▶ 人工看图决策
   mapping_ledger     ──▶ │              │
                          └──────────────┘
```

## 二、目录内容


| 文件                | 是什么                             | 会不会写盘            |
| ----------------- | ------------------------------- | ---------------- |
| `mapping_core.py` | 核心库：XML 原地读写、几何计算、配对式 diff、台账读写 | 不写，只是被 import    |
| `1_生成变更集.py`      | **第 1 步**：比对子图与裁切记录，算出该改什么      | 只写 `--output` 目录 |
| `2_应用变更集.py`      | **第 2 步**：把变更集真正写进原图总库          | 加 `--apply` 才写   |
| `4_审核可视化.py`      | **第 3 步**：渲染对比图 + 网页人工决策 + 决策回灌 | 只写审核目录           |
| `3_回滚.py`         | **应急**：按备份把原图 XML 还原回去，并撤回对应台账 | 加 `--apply` 才写   |


编号 1→2→4→2 是常规顺序（先跑自动的，再审核人工的，再跑一次补充变更集），`3_回滚.py` 只在出事时用。

## 三、完整流程



### 数据流总览

```
子图 Annotations ──┐
crop_mapping.json ─┼─→ ① 1_生成变更集.py ─→ changeset.json ──→ ② 2_应用变更集.py ─→ 原图总库
原图 Annotations ──┘          │                                        │
mapping_ledger.jsonl ─────────┘                                        ├─→ backup_<时间戳>/ ─→ ⑤ 3_回滚.py
                              │                                        └─→ mapping_ledger.jsonl
                              └─→ review_queue.json
                                        │
                                        ↓ ③ 4_审核可视化.py render --serve
                                   网页上逐条看图选方案
                                        │
                                   decisions.json（实时存服务器）
                                        │
                                        ↓ 点「生成补充变更集」
                                supplement_changeset.json ─→ ④ 2_应用变更集.py
```

下面按 ①②③④ 逐步说明。示例统一用 `gd_data`，换数据集只改路径。

---



### ① 生成变更集（纯只读，不碰任何原图）

```bash
cd /raid/wtj/yh_modify_defect_datasets/2-defect_mapping

python 1_生成变更集.py \
  --dataset-dir /raid/datasets_defect_2026/datasets_val/全量_正样本/gd_data \
  --original-xml /raid/Nas-122/项目数据/输电项目/缺陷/标记样本库/全图测试集2026/Annotations \
  --output ./输出/gd_data
```

**自动推断的东西**（不用手写）：

- 部件类型按目录名推断：`dx_data→ddx`、`gd_data→gd`、`gt_data→gt`、`jyz_data→jyz`、`jc_data→jc`，
推断不出会报错，用 `--component-type` 指定
- 子图 XML 目录默认 `<dataset-dir>/Annotations`
- `crop_mapping*.json` 在数据集目录下自动发现（正样本/负样本两个文件都会读）
- 台账默认放在原图 XML 目录的**上一级**，跟着原图库走。`1_生成变更集.py` **自动检索**这份文件（不存在就当空台账）；不加 `--ledger` 不用手写路径

**输出到** `./输出/gd_data/`：


| 文件                  | 内容                  |
| ------------------- | ------------------- |
| `changeset.json`    | 能自动执行的变更，交给第 ② 步    |
| `review_queue.json` | 需要人工看图确认的条目，交给第 ③ 步 |
| `report.txt`        | 统计报告，**跑完先看这个**     |


`report.txt` 分 6 节：扫描概况 / 逐子图 diff 结果 / 去重与合并 / 待人工确认 / 最终变更集 / 提示。
重点看第四节「待人工确认」的条数和第五节「变更总条数」是否符合预期。

### ② 应用变更集（先预演，再写入）

```bash
# 预演：校验 md5、校验每条变更能否精确定位，一个字节都不写
python 2_应用变更集.py --changeset ./输出/gd_data/changeset.json

# 预演全部通过后，真正写入（会先备份将被修改的那些 XML）
python 2_应用变更集.py --changeset ./输出/gd_data/changeset.json --apply
```

写入过程分 4 步，屏幕上会逐步打印：

1. **preflight**：逐文件核对 md5 与生成变更集时一致、逐条变更核对目标框在原图里恰好命中一次。
  任何一项不过就**整体中止**，不会出现"改了一半"
2. **备份**：只复制将被修改的那些 XML 到 `backup_<时间戳>/files/`，并写 `manifest.json`
3. **写入**：每个文件"临时文件 + `os.replace` + `fsync`"原子替换
4. **记台账**：把每条变更追加到 `mapping_ledger.jsonl`

不加 `--yes` 时会有一次交互确认，需要手输 `yes`。

### ③ 人工确认剩下的疑难条目



#### 渲染 + 起服务（远程连 Linux 服务器时推荐这个，一步到位）

```bash
python 4_审核可视化.py render \
  --review-queue ./输出/gd_data/review_queue.json \
  --dataset-dir /raid/datasets_defect_2026/datasets_val/全量_正样本/gd_data \
  --original-images /raid/Nas-122/项目数据/输电项目/缺陷/标记样本库/全图测试集2026/images \
  --output ./输出/gd_data/review --serve
```

图片渲染只需做一次。之后想重新打开审核页面，直接起服务即可：

```bash
python 4_审核可视化.py serve --review-dir ./输出/gd_data/review
```

服务默认监听 `127.0.0.1:8770`，端口被占用会自动往后找（最多试 50 个，**启动横幅里会打印实际端口**）。

**输出到** `--output`**（示例** `./输出/gd_data/review/`**）**：


| 文件                 | 谁写的         | 内容                                                                                                                    |
| ------------------ | ----------- | --------------------------------------------------------------------------------------------------------------------- |
| `index.html`       | `render`    | 审核网页，条目列表和对照图都嵌在这一页里                                                                                                  |
| `review_meta.json` | `render`    | 上下文：数据集名、`review_queue` / `changeset` 路径、原图 XML 目录、台账路径、补充变更集要写到哪。`serve` 靠它定位，**重新 render 会覆盖**（不动 `decisions.json`） |
| `decisions.json`   | 网页点选时（起了服务） | 人工决策。键是条目 `id`（队列顺序），值是方案 `key`（如 `union` / `replace` / `delete` / `reject`）。**render 不会覆盖已有决策**                      |
| `images/`          | `render`    | 对照图。每条 `{id}_{reason}_full.jpg` 全图定位、`_orig.jpg` 原图局部、`_sub.jpg` 子图；每个可选方案另有 `_opt_{方案key}.jpg` 效果图                   |


网页上点「生成补充变更集」时，**不写在** `review/` **里**，而是写到与 `review_queue.json` 同级：


| 文件                                                                          | 谁写的                     | 内容                                                         |
| --------------------------------------------------------------------------- | ----------------------- | ---------------------------------------------------------- |
| `../supplement_changeset.json`（示例 `./输出/gd_data/supplement_changeset.json`） | 网页按钮或 `build-changeset` | 格式与 `changeset.json` 相同，交给第 ② 步 `--apply`。只包含你采纳的方案，驳回的不写入 |


离线打开 `index.html` 时决策在浏览器 localStorage，需点「下载 decisions.json」得到同结构的文件，再用 `build-changeset` 生成上面那份补充变更集。

条目 `id` 按 `review_queue.json` 的顺序生成。重新跑 `1_生成变更集.py` 后 id 会变，旧 `decisions.json` 对不上，要重新审。

#### 网页上看什么、怎么选

每条待确认项会渲染 3 张对照图（可并排看、点击放大）：


| 图        | 作用                                        |
| -------- | ----------------------------------------- |
| **全图定位** | 整张原图缩略，蓝色虚线标出部件裁切区，红框 + 十字线指向缺陷位置         |
| **原图局部** | 冲突处放大。裁切区**外面压暗**（子图里看不到的区域），被截断的部分**垫红** |
| **子图**   | 人工清洗后的子图，标出人工改过/新增的框                      |


每个可选方案还各有一张**效果图**：灰色虚线是当前框，红色实线是采纳后的框，
有变化的边用品红加粗并标注 `左边 1234 → 1240` 这样的数值 —— `union` 和 `replace`
这类只差几条边的方案，不标出来肉眼根本分不清。

**点卡片底部的文字条**才是选中方案；点图片只是放大预览（放大后再点一次看 1:1 原始像素）。

键盘快捷键（条目多的时候快很多）：


| 按键        | 作用                      |
| --------- | ----------------------- |
| `j` / `k` | 下一条 / 上一条               |
| `1`~`9`   | 选中第 N 个方案（选完自动跳到下一条未决策） |
| `0`       | 驳回（原图保持不变）              |
| `n`       | 跳到下一条未决策                |
| `Esc`     | 关闭放大                    |


顶部下拉框可按「仅未决策 / 仅已决策 / 某类原因」过滤。

#### 决策存哪里

**起了服务时**：每点一次自动 POST 到服务器，实时落盘到 `review/decisions.json`。
关掉浏览器、换台机器接着审都不会丢，不需要在 Windows 和 Linux 之间倒腾文件。
页面左上角的状态标签会显示是否连上服务器（绿色「已连接服务器」/ 黄色「未连接」）。

**没起服务时**（直接用浏览器打开 `review/index.html`）：决策存在浏览器 localStorage，
必须点「下载 decisions.json」导出，再传回服务器用命令行回灌（见下）。

#### 远程审核怎么连

在 Windows 上通过 Cursor / VSCode Remote-SSH 连着 Linux 服务器时，服务一起来端口就会
**自动转发**到本机，直接在 Windows 浏览器打开横幅里那个 `http://localhost:<端口>/` 即可。

如果没有自动转发，在 Windows 本机手动开个隧道：

```bash
ssh -L 8770:localhost:8770 <用户名>@<服务器地址>
```

要让同局域网的其他机器直连，起服务时加 `--host 0.0.0.0`（注意这会把页面暴露到局域网）。

### ⑤ 出问题了要还原

```bash
python 3_回滚.py --manifest ./输出/gd_data/backup_20260813_143000/manifest.json          # 预演
python 3_回滚.py --manifest ./输出/gd_data/backup_20260813_143000/manifest.json --apply  # 还原
```

回滚前会逐个核对 md5：

- 现场文件 md5 == `md5_before` → 本来就没改过或已回滚过，跳过
- 备份文件 md5 != `md5_before` → 备份自身损坏，中止（除非加 `--force`）

回滚 XML 的同时，会撤回**这次备份对应那一次 `--apply`** 写入的台账行，其它数据集、更早的写入都留下。
下次再跑 `1_生成变更集.py` 会重新算出这批变更，不会被台账当成已应用而跳过。
撤回前会把当前台账复制一份到备份目录 `ledger_before_rollback_<时间戳>.jsonl`。

如果这些 XML 在本次备份之后又被改过（已经 apply 了补充变更集，或下一个数据集已经写过），**默认中止**。
请先回滚更晚的那次备份；确认要连同后续写入一起作废时再加 `--force`（会把那些更晚的台账行一并撤回）。
只想还原 XML、不动台账时用 `--skip-ledger`（下次生成变更集会把这批框当成已应用，一般不要用）。

## 五、核心算法（为什么这么设计）



### 1. 配对式 diff —— 最关键的一环

**不能**用"精确匹配，剩下的一律算增删"。人工把框挪动 1 个像素就会被判成「删一个 + 加一个」；
对 `was_clipped` 的框，这会把原图里的**完整框删掉、换成一个截断的小框**。
实测 gt_data 就有 35 处这种 ≤2 像素的取整噪声。

所以是四步：

1. `(类名, 坐标)` 完全一致 → `unchanged`
2. 剩下的按 IoU 降序贪心配对（默认 `--pair-iou 0.5`）→ `modified`，并区分改的是类别还是坐标
3. 仍未配上的旧框 → `deleted`
4. 仍未配上的新框 → `added`

四角偏移 ≤ `--noise-tolerance`（默认 2px）的坐标变化视为取整噪声，不算改动。

### 2. 在原图中定位目标框 —— 用精确匹配，不用 IoU

判据是 `(类名, 精确坐标)` **完全相同**。实测 5 个验证集数据集共 67776 条裁切记录 100% 能精确命中；
而 IoU 模糊匹配在挂点这种重叠框密集的场景会匹配到错误的框。

gd 的类别映射是多对一不可逆的，`crop_mapping` 里只存了映射后的名字。所以实际判据是
「**原图类名过一遍** `class_mapping` **后 == 子图里的名字，且坐标完全相同**」，
这样能反查出原图里的真实细分类名（如 `nzxj_lsqdp`）。命中 0 个或多个都不动，交人工确认。

### 3. 操作决策表


| 子图上的操作 | `was_clipped`       | 处理                                    |
| ------ | ------------------- | ------------------------------------- |
| 未改动    | —                   | 不动                                    |
| 改类别    | 任意                  | **就地**改原图完整框的 `<name>`                |
| 改框     | `false`             | 就地改坐标为「子图新框 + 部件框左上角偏移」               |
| 改框     | `true`，新框**不贴**裁切边界 | 直接替换（人工把框缩到了部件内部，是完整的框）               |
| 改框     | `true`，新框**仍贴**裁切边界 | ⚠️ 待确认（原图里很可能还是截断的，直接替换会把框改小）         |
| 删除     | `false`             | 删除原图的 `<object>` 节点                   |
| 删除     | `true`              | ⚠️ 待确认（原图框有一截在部件框外，人工没看到过）            |
| 新增     | —                   | 换算成原图坐标；与原图已有框 IoU≥0.5 时：同类名跳过，异类名待确认 |


「改类别」永远是**就地改** `<name>` **文本**，绝不做「删旧框 + 加新框」。
否则原图会同时存在 `lmsd` 和 `lslmqk` 两个重合的框，下次裁切就真的裁出两个了。

### 4. 跨子图一致性

同一个原图缺陷被多个子图裁到时，把各子图的结论汇总判断：


| 情况            | 处理                                                        |
| ------------- | --------------------------------------------------------- |
| 删除 与 保留/修改 并存 | **冲突**，交人工（删除是破坏性的，必须所有子图一致）                              |
| 多个互不相同的修改     | **冲突**，交人工                                                |
| 修改 与 未改动 并存   | 采纳修改（通常是人工只在其中一个子图上作业过）；加 `--strict-consistency` 可把这种也算冲突 |


实测 gd_data 有 5290 组缺陷被多个子图同时裁到，其中 222 组结论矛盾被拦下。

### 5. 新增框去重

**先跨子图合并，再去对原图已有框**（顺序反了会把同一位置拆成多张审核卡）。

1. **多个子图在同一位置各画一个**：同类名合并成一条，异类名交人工确认。
  **同一个子图内部的重叠框不参与去重** —— 那是人工有意画的两个不同缺陷。
2. **与原图已有框重叠**（IoU ≥ `--dup-iou`）：这些缺陷原图里本来就标了，只是裁切时被面积阈值
  或类别过滤挡掉，人工在子图里以为漏标就又画了一个。同类名（或过 `class_mapping` 后同名）
   直接跳过，异类名交人工确认（一张卡：`retag` 改原框类别 / `add` **只写一个框**）。

点「生成补充变更集」时还会再收一次：旧队列里同一位置的两张卡如果都选了 `add` 或都选了 `retag`，只保留一条，避免写成两个框。

实测 gd_data：跳过 40 个、合并 662 个、530 个异类名交人工。

### 6. 变更台账 `mapping_ledger.jsonl`

挂点、绝缘子、杆塔等多次回写**同一份原图总库**，都用**这一份**台账，按「原图某一个框」记账，不是按数据集各写一份。

默认路径：原图 XML 目录的上一级 `mapping_ledger.jsonl`（例如 `全图测试集2026/mapping_ledger.jsonl`）。
`1_生成变更集.py` 根据 `--original-xml` **自动检索**（文件不存在当空，不报错）；
`2_应用变更集.py --apply` 成功写入原图后**追加**一行，只增不覆盖。预演不写台账。
`3_回滚.py --apply` 会整文件重写台账，只去掉这次备份对应的行。

- 这个框已经按**同样结果**写过 → 生成变更集时跳过（可重复跑，只处理新清洗）
- 这个框写过，但这次要改成**不同结果** → `ledger_conflict`，交人工确认（不自动覆盖）
- 不同部件改的是不同框 → 互不冲突，继续往同一文件后面追加

必须一个数据集 ①→④ 跑完再开下一个，否则后一个生成变更集时还看不到前一个刚 apply 的记录。
回滚会撤回**这次 apply 对应的台账行**（不是整份清空，也不是按数据集全删），不必手改 jsonl。

## 六、注意事项（红线）

1. `1_生成变更集.py` **是纯只读的**，随便跑，不会碰原图。
2. `2_应用变更集.py` **/** `3_回滚.py` **默认都是 dry-run**，必须显式 `--apply` 才写盘。
  养成习惯：先不带 `--apply` 跑一遍，看清楚统计再加。
3. **preflight 不通过就是整体中止**。已经在审核或审完时，优先加 `--skip-invalid` 再预演，
  看跳过这些文件后结果是否可接受；**不要轻易重跑** `1_生成变更集.py`，否则队列 id 会变，要重新审核。
  `--no-md5-check` 仍然不要用。
4. **备份别删**。`backup_<时间戳>/` 是唯一的还原依据，确认这批改动没问题之前不要清理。
5. **XML 字节级无损**：不重建 XML，`<path>`/`<source>`/`<score>` 等字段、tab 缩进、
  CRLF/LF 换行、中文实体写法（`号` vs 字面中文）、文件末尾换行全部原样保留。
   已抽样验证 4003 个原图 XML 空改写后**字节完全一致**。
6. **作用域限制**：只碰本数据集 `defect_classes` 范围内、且能被裁切记录定位到的框。
  原图库里另外那 100 多个类别（含 `均压环`、`玻璃` 等中文类名和 `lb_Xs` 这类笔误）一个都不动。
7. **多个数据集回写同一个原图库时，一个一个来**：跑完 gd_data 的 ①→④ 全流程，再开始 gt_data。
  台账靠 `--apply` 时才写入，同时跑两个会漏掉冲突检测。
8. **回滚后进先出**：先回滚更晚的备份（补充变更集、后一个数据集）。回滚会同时撤回对应台账，不要手改 jsonl。

## 七、数据结构



### `changeset.json`

```jsonc
{
  "version": 1,
  "meta": { "dataset": "gd_data", "component_type": "gd",
            "original_xml_dir": "...", "ledger": "...", "pair_iou": 0.5, ... },
  "files": {
    "某张原图.xml": {
      "md5": "生成变更集时该文件的 md5，写入前会重新校验",
      "changes": [
        // 改类别：就地把 target 那个框的 name 改成 new_name
        {"action":"set_name", "target_name":"nzxj_lsqdp", "target_bbox":[...],
         "new_name":"lsqbm", "was_clipped":false, "sources":["xxx_crop1.xml"]},
        // 改坐标
        {"action":"set_bbox", "target_name":"...", "target_bbox":[...], "new_bbox":[...]},
        // 类别和坐标一起改
        {"action":"set_name_bbox", "target_name":"...", "target_bbox":[...],
         "new_name":"...", "new_bbox":[...]},
        // 删除
        {"action":"delete", "target_name":"...", "target_bbox":[...]},
        // 新增
        {"action":"add", "new_name":"...", "new_bbox":[...]}
      ]
    }
  }
}
```

`target_name` 是原图里的**真实类名**（可能是映射前的细分类名），`target_bbox` 是原图里的
**精确坐标**，两者共同唯一确定要改哪个框。`sources` 记录这条变更来自哪些子图。

### `review_queue.json`

每条待确认项都带 `options` —— 一组可直接选用的处理方案，每个方案里的 `change`
就是 `changeset.json` 里 `changes[]` 的元素格式，所以回灌是零转换组装。


| `reason`                                | 含义                   | 可选方案                              |
| --------------------------------------- | -------------------- | --------------------------------- |
| `clipped_deleted`                       | 被截断的缺陷在子图里被删了        | `delete`                          |
| `clipped_bbox_modified_border`          | 被截断的缺陷改了框、新框仍贴边      | `union` / `replace` / `name_only` |
| `added_overlaps_existing`               | 新增框与原图已有框重叠但类名不同     | `retag`（改原框类别）/ `add`（当成两个缺陷）     |
| `cross_crop_inconsistent`               | 多个子图对同一缺陷的结论矛盾       | 每个候选结论一个方案                        |
| `cross_crop_added_conflict`             | 多个子图在同位置新增了不同类别      | 每个**不重复类别**一个方案 + 类别组合 / `all`（每类只写一个框） |
| `ledger_conflict`                       | 该框已被其他数据集改过且结果不同     | `force`（覆盖）                       |
| `added_out_of_scope`                    | 新增框类别不在本数据集作用域内      | `add`                             |
| `added_invalid_bbox`                    | 换算到原图后坐标非法（越界或宽高为 0） | 无                                 |
| `target_not_found` / `target_ambiguous` | 原图里找不到 / 有多个重复框      | 无（需要先查清原因）                        |
| `sub_xml_unreadable`                    | 子图 XML 解析失败          | 无                                 |


没有方案的条目只能驳回，或者查清原因后手工处理。

`union` **方案的含义**：人工只能看到部件框以内的那一截，所以**贴着裁切边界的那几条边保留
原图坐标**（框在原图里还往外延伸），**没贴边的那几条边采用人工的新坐标**。

### `mapping_ledger.jsonl`

一份原图库一份台账。生成变更集自动读、`--apply` 才追加；回滚会撤回对应行。每行一条已写入的变更：

```jsonc
{"applied_at":"...", "dataset":"gd_data", "component_type":"gd", "changeset":"...",
 "original_xml":"某张原图.xml", "action":"set_name",
 "before_name":"nzxj_lsqdp", "before_bbox":[...],
 "after_name":"lsqbm", "after_bbox":[...], "sources":["xxx_crop1.xml"]}
```

## 八、常见问题

**Q：裁切记录里有、子图目录里已经没有的条目怎么处理？**
按「未参与清洗」跳过，**绝不当作删除 GT**。训练集尤其重要：`datasets_train/.../dx_data` 的
`crop_mapping` 有 231968 条，而 `Annotations` 只剩 43255 个 XML（其余被主动剔除了）。
如果把缺失当删除，会大规模误删总库标注。

**Q：**`crop_mapping` **里的** `original_img_path` **能用吗？**
不能。验证集那批记录里写的是 `/raid/datasets_defect_2026/全图测试集/...`，该目录已不存在
（原图库搬到了 Nas-122）。本工具只用 `original_defect_xml` 这个纯文件名，配合命令行指定的目录。

**Q：写回映射后的类名（如** `lslmqk`**），下次裁切会不会重复裁出两个框？**
不会。裁切程序是对每个 `<object>` **逐个就地改名**，一个框永远只产生一个框；而且
`overlap_thresholds` 查的是映射后的名字，`lmsd` 和 `lslmqk` 用的是同一个阈值，裁切行为一致。
但代价是：写回后这个框原本是 `lmsd` 还是 `xjjsd` 的信息就**永久丢失**了。

**Q：预演报** `md5_mismatch` **怎么办？**
说明这个原图 XML 在生成变更集之后被改动过了（可能是别的数据集刚写过）。
正确做法是重新跑 `1_生成变更集.py` 生成最新的变更集，而不是加 `--no-md5-check` 绕过。

**Q：预演报** `target_not_found` **怎么办？**
同上，多半是原图已被改动。台账里有记录的会被自动识别为「已应用」而跳过；
如果台账里也没有，说明有工具之外的改动，需要先查清楚。

**Q：审核页面打不开 / 一直转圈？**
页面是先用本地数据把列表画出来、再在后台探测服务器（带 6 秒超时）的，服务端不通也不会卡成空白。
如果整页打不开，先确认横幅里打印的**实际端口**（可能不是 8770），再确认端口转发是否生效。

**Q：想重新渲染对比图，之前的决策会丢吗？**
不会。决策存在 `review/decisions.json`，`render` 不会动它。但条目 `id` 是按队列顺序生成的，
所以**重新跑** `1_生成变更集.py` **之后 id 会变，旧决策就对不上了** —— 这种情况下要重新审。

**Q：回滚之后再生成变更集，还会把这批框当成已应用而跳过吗？**
不会。回滚会撤回这次 apply 对应的台账行，生成变更集会重新算。不要手改 jsonl。
若回滚时报「这些 XML 在本次备份之后又有台账写入」，先回滚更晚的那次备份。

**Q：原图库搬家了怎么办？**
`2_应用变更集.py` 和 `3_回滚.py` 都支持 `--original-xml` 覆盖记录在文件里的旧路径。
台账也要跟着一起搬（它默认在原图 XML 目录的上一级）。
